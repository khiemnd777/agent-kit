# Project context

Keep stable domain/design/constraints here. Current progress belongs in project-state.md; outcomes belong in project-plan.md and historical approvals/evidence in tasks/decisions. Do not import another project's implementation authority.

This is an optional fresh project context summary; the task/issue remains the delivery source of truth. It contains no approved product, stack or execution authority. The named shared-record owner updates it when documentation writes are authorized.

Record each accepted decision with its human source, date, rationale and affected tasks. Preserve exact labels and business identifiers. Keep proposals separate. Do not import prior-project approvals, private memory or kit verification results as project facts.

## Overall picture for roadmap delivery

When a roadmap is actually agreed, record its revision and preplanned package IDs/names/order here before implementation. Link intended outcomes, dependencies and observable acceptance in project-plan.md; live progress belongs only in project-state.md. Mark unconfirmed work and its decision point explicitly. Do not infer a new next package after finishing the current one; material changes need an amended approved plan.

The [handoff criteria and templates](handoff-templates.md) distinguish one handoff from roadmap delivery. Every plan declares delivery type, rationale and parent roadmap directly in the conversation. A small package inside a roadmap retains its position and acceptance stops. This blank template contains no actual roadmap or authority; an adopting project's owner fills it only within authorized documentation work.
