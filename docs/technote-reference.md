# TechNote extended method

Optional reference for a requested detailed explanation or selected diagram, interactive website or video. The [short guide](technote.md) is sufficient for routine updates. These techniques do not introduce approval stages, require every field in every message, or expand implementation scope.

## Evidence and language

Inspect relevant source before explaining existing behavior. Distinguish observed facts, proposals and unknowns close to their claims. A diagram or simulation illustrates behavior; it does not verify the application. Separate a supported cause from a hypothesis and say what evidence could resolve it.

Use the requested language, otherwise English. Preserve product labels, identifiers and quotations. Keep terminology stable, sentences concrete and paragraphs focused. This style draws on technical writing principles; it is not ASD-STE100 certification or a controlled-vocabulary claim.

## Detailed technical note

Select detail that changes a decision: the affected component, scope, evidence, tradeoff or remaining action. An opening update can state the intended outcome and how uncertainty will be resolved. A closing update can state what changed, why, observed checks and meaningful limits. Omit fields already clear from the conversation.

Progress updates should add a finding, decision or blocker rather than a log of routine tools. A long task may link one checkpoint instead of duplicating its state. An explanation never grants implementation, Git, paid-service or publication authority.

## Diagrams

Choose a supported format and focus each diagram on one relationship: flow, responsibility, topology or state transitions. Show conditions and outcomes that matter. Label proposed or unknown behavior and explain omitted scope. Reuse the topic's established terminology.

Prefer a compact static diagram when that fully explains the issue. Check rendering with available capabilities when delivering a rendered artifact; disclose if only diagram source was checked.

## Interactive explanation

Deliver a usable interactive explanation when that medium is requested. Use Previous, Next and Replay controls where the explanation has stages; for a nonsequential model, provide appropriate navigation and reset. Distinguish sample/simulated values from observations.

Check important navigation, reset behavior, readability and relevant viewports with available tools. Deliver a usable local or authorized hosted result. Public hosting needs actual authority. If the required tool or destination is unavailable, state what is missing; prose is not a completed website.

## Video

Deliver an actual exported video when requested and feasible. Plan the needed script, visuals and narration, preserving the requested language and topic. Check available capture, audio and export capabilities before production. Protect private source material and label illustrations.

Verify the exported file, readability, timing and relevant audio/captions with available tools. State viewing/listening limits. A storyboard or script can be an explicitly agreed alternative but must not be presented as the completed video.

## Examples

- **Investigation:** Explain why overlapping bookings succeed using the inspected transaction path and relevant checks. Keep an untested concurrency hypothesis explicit.
- **Direct diagram:** A request for Level 2 approval flow selects the diagram directly; no preliminary Level 1 lesson is needed.
- **Interactive model:** A retry-outcome explanation can show success, rejection and unknown outcome states with reset/replay and clearly illustrative data.
- **Unavailable export:** Report the missing rendering/export capability and the undelivered video. Do not claim a written script completes it.
