# Approved-template application acceptance checklist

Use this checklist only for a task applying an internal or user-supplied template approved by the human. Copy the relevant rows into the owned task record or link a task-specific copy. Do not create a second authoritative task state. Record the template source, version/revision and hash, approved differences, representative screen, comparison artifacts and matched viewport dimensions before evaluating rows. See the [workflow](team-workflow.md#applying-an-approved-template) and [reference](../.agents/references/template-application.md).

Each row needs a specific criterion, screen, role, data state, viewport, expected result, evidence link or location, PASS/FAIL/NOT_RUN and owner. For structural rows, name the template element in the criterion and its target position in the expected result; this maps template to implementation without another state record. Replace the bracketed fields; add rows for task-specific controls and states. PASS requires observed evidence for that exact condition. FAIL records the mismatch. NOT_RUN records the missing prerequisite, reason, owner and next action. One screenshot does not prove a sequence or keyboard access.

Expand the state row into separate rows for each applicable condition. If a preview, state or action does not exist in the approved template, mark it not applicable in the task record with the reason rather than claiming PASS. Do not execute a data-changing action outside the task's permission scope; record NOT_RUN with the owner and next action. A page-level no-overflow result does not establish that controls inside containers are visible or reachable. Build/source PASS is Code integrated evidence only; keep Behavior/UI verified and Human accepted separate. `CODE_COMPLETE_UNTESTED` applies only to a human-requested self-test source handoff and does not close a verified-template objective.
